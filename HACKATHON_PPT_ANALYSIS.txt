1. COMPREHENSIVE ANALYSIS OF EXISTING PROJECT
================================================================================
A. Core Concept & Domain:
   way-2-gather is a production-ready, peer-to-peer carpooling web platform
   specifically architected for daily commuters and inter-city travelers in
   Tamil Nadu. It addresses the twin crises of urban traffic congestion and
   unaffordable solo cab fares by matching vehicle owners (Hosts/Drivers) with
   daily commuters (Seekers) along shared road travel corridors.

B. What is Actually Implemented (Verified in Codebase):
   1. Multi-Tier Microservice Topology:
      - Frontend: React 18, Vite, Mapbox GL JS (v3), Socket.io Client,
        Vanilla CSS Design Tokens, Lucide Icons.
      - Gateway & Business API: Node.js, Express, MongoDB (Mongoose ORM),
        Socket.io Server, JWT Auth, Bcrypt, SHA-256 Crypto.
      - AI & Spatial Engine: Python 3, FastAPI, Uvicorn, XGBoost Classifier,
        NumPy, Haversine Vector Math, Orthogonal Point-to-Segment Projection.

   2. Authentication & Trust Framework:
      - User registration with mandatory Government ID document upload.
      - Privacy-preserving Aadhaar KYC verification: raw Aadhaar numbers are
        hashed via SHA-256 (one-way cryptographic digest); only masked last-4
        digits are stored for verification display.
      - Role flexibility: users can act as Driver, Seeker, or both.

   3. Ride Creation & Publishing (Host Flow):
      - Hosts publish scheduled rides with vehicle specifications (plate number,
        model, color), available seat inventory (1-6 seats), start/destination
        points, and an optional Women-Only carpool toggle.
      - Rides are indexed in MongoDB using GeoJSON 'Point' representations with
        a '2dsphere' spatial index.

   4. Clean Seeker Ride Search (Zero Bias):
      - Seeker pickup and dropoff fields initialize blank (no pre-decided
        assumptions).
      - Interactive Map markers (Red Driver markers and Green Seeker markers)
        appear dynamically only after searching or requesting a ride.

   5. Two-Stage Candidate Filtering & AI Inference:
      - Stage 1 (Fast Hard Filtering in Node/MongoDB):
        Instantly filters active rides by available seat count ($gte), departure
        window (+/- 180 mins), and 50km geospatial proximity ($near).
      - Stage 2 (6D Feature Vector & XGBoost in Python):
        For every candidate, the engine computes:
        a) detour_distance_km
        b) detour_time_mins (at average 40 km/h)
        c) origin_proximity_km (pickup to driver path)
        d) destination_proximity_km (dropoff to driver path)
        e) time_difference_mins
        f) route_overlap_ratio (0.0 to 1.0)
        An XGBoost Classifier infers the Match Acceptance Probability (0-100%)
        with an ensemble logistic regressor fallback.

   6. Secure Handshake & Real-Time Execution:
      - Booking generates an algorithmic 4-digit Handshake OTP.
      - Host accepts ride via Socket.io ('accept_ride' -> 'ride_started').
      - Both peers transition automatically to the live tracking corridor.

   7. Real Road Network Routing & Live Simulation:
      - Route lines query the Mapbox Directions API ('mapbox/driving') with an
        Open Source Routing Machine (OSRM) fallback to trace actual road networks
        rather than straight-line cuts.
      - Live GPS tracking via WebSockets ('location_update').
      - In-app simulation drives the vehicle along actual road coordinate
        waypoints, dynamically shortening the remaining path and updating ETA.

   8. Safety Corridor & Automatic SOS Deviation Warning:
      - Continuously evaluates vehicle GPS against the planned multi-point
        route corridor.
      - If shortest orthogonal distance exceeds 1.0 km (or 1.5 km threshold),
        an automated SOS alert is triggered across WebSockets and dispatched.

   9. Economics & Rating Integrity:
      - Fair cost-sharing rule: strictly ₹10 per km for the shared distance.
      - Environmental metric: computes CO2 offset at 0.192 kg CO2/km.
      - Separate Driver Rating (e.g. 5.0) and Seeker Rating (e.g. 5.0).
      - Automated Harassment Strike Engine: accumulating 5 severe strikes
        automatically blocks the user's account and cancels all active rides.

SLIDE 7: CORE ENGINEERING & ALGORITHMIC LOGIC
--------------------------------------------------------------------------------
Criteria: Technical Understanding & Viva
Content:
1. The 6-Dimensional Feature Vector:
   X = [d_detour, t_detour, prox_orig, prox_dest, Δt_departure, ratio_overlap]
   Where:
   - ratio_overlap = (Rider Distance / Driver Distance) * Detour Attenuation
   - t_detour = d_detour * 1.5 mins (calibrated urban transit speed)

2. XGBoost Inference & Calibrated Logistic Fallback:
   Trained on realistic commuter distributions. Computes acceptance probability:
   Logit = 2.8 - 0.55(d_detour) - 0.15(t_detour) - 0.40(prox_orig)
           - 0.40(prox_dest) - 0.06(Δt) + 2.50(ratio_overlap)
   P(Acceptance) = 1 / (1 + e^(-Logit))

3. Orthogonal Point-to-Segment Deviation Formula:
   For vehicle position P(px, py) and corridor segment AB:
   t = clamp(((P - A) • (B - A)) / |B - A|², 0, 1)
   Projection P_proj = A + t * (B - A)
   Distance = Haversine(P, P_proj)
   If min(Distance) > 1.0 km -> Automated SOS Trigger.

4. Transparent Cost Equation:
   Total Fare = Shared Distance (km) * ₹10/km * Seats
   CO2 Saved = Shared Distance (km) * 0.192 kg CO2/km

4. GAPS IN THE PROJECT RELATIVE TO JUDGING CRITERIA & VIVA DEFENSE
================================================================================

Q1: "Why did you use XGBoost instead of a simple distance radius query?"
A1: Simple distance radius fails in the real world: two commuters may be 500m
    apart geographically, but separated by a river, highway divider, or traveling
    in opposite directions. Our 6D feature vector captures route overlap ratio,
    exact detour distance, and detour time, predicting whether a driver will
    actually accept the seeker.

Q2: "What dataset was used to train the XGBoost model?"
A2: We initialized the classifier using a calibrated domain synthetic distribution
    of 1,500 samples modeling realistic Tamil Nadu urban commuting parameters.
    The production architecture records actual user accept/decline outcomes in
    MongoDB to continuously fine-tune the model with real-world feedback.

Q3: "What happens if the Python AI service crashes during peak hours?"
A3: We built a multi-stage high-availability fallback. If the Python FastAPI
    service is unavailable, the Node.js backend smoothly degrades to in-engine
    proximity scoring and a calibrated logistic regression formula without crashing
    the user's booking experience.

Q4: "How is user privacy preserved during mandatory Aadhaar verification?"
A4: We never store unencrypted 12-digit Aadhaar numbers. The backend hashes the
    Aadhaar input using SHA-256 with a unique digest, storing only the hash and
    masked last 4 digits for verification badges.

Q5: "Why did you set the pricing strictly at ₹10/km?"
A5: In Tamil Nadu, typical solo cab rates are ₹20-25/km plus base fares and surge.
    ₹10/km covers vehicle fuel and maintenance costs for the host while cutting
    commuter transit expenses by over 50%, ensuring an equitable, non-commercial
    carpooling cost-split.
